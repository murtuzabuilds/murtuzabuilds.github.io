How I build AI products

A model for the judgment calls. Plain code for the promises.

Four products, one method. Three use a language model for one narrow job each, and one deliberately uses none. Every number on this page was measured, and the case studies at the end show the tests behind them.

The method

Five decisions I make before I write a prompt.

1

Where does a model belong?

Where language is messy and a person checks the result. Where a promise has to hold every time, plain code decides.

In Umbra the model drafts a rule and fixed rules enforce it. In CardRight it names a store's category and the math picks the card. In Conatus it writes the words of a plan and the rules set every date. In Outpost no model is involved in the decision at all.

2

Which model?

Test the job, not the leaderboard: accuracy against a rules-only baseline on a fixed test set, speed for the wait the user will tolerate, cost per call, and where it is allowed to run.

I chose gpt-oss-120b, OpenAI's open-weight model, served by Groq. A Gemini Flash model drafted correctly too, but answered several times slower and ran out of free daily quota mid-test. Open weights matter for Umbra's buyer: a regulated company could run the same model in its own cloud.

3

Prove it before launch

Write the test set and answer key before scoring. Include cases it should refuse. Keep a baseline, publish the misses, and never change the rules after seeing the results.

Umbra was scored on 51 policy sentences, Conatus on 30 goals including health-risk and crisis messages, and CardRight on 18 store names it was never tuned on. Conatus's strict word-match rule fails 7 plans a person would call on-topic, and it stayed as written.

4

Design the failure first

Every model call has a timeout, a fallback that says so on screen, and a checker that drops anything outside the allowed shape.

Umbra falls back to its rules after 8 seconds. CardRight keeps its name rules as a second opinion because the model's one miss was confident and wrong. Conatus catches crisis words before any model call.

5

Make cost follow value

Call the model when value is created, not on every event. Then serving a customer does not get more expensive as they use the product more.

Umbra calls the model when someone writes a policy, a few times a week, while inspecting every prompt is plain code. CardRight only asks about stores it does not know. Outpost decides in about two microseconds at no cost per action.

Trade-offs

What I gave up, and why.

Speed over a model that was just as correct

Gemini Flash drafted Umbra rules correctly but several times slower. For a box a person waits on, speed decided it.

Cost: less headroom if a harder drafting job comes later.

Safe refusal over usefulness

When a policy sentence hides an instruction, Umbra's model refuses the whole sentence instead of drafting the genuine half. It handled 2 of 4 such cases and drafted nothing unsafe.

Cost: the person rewrites the sentence. Next on the roadmap.

A second opinion over trusting the model

CardRight's model called Midstate Gas Company a gas station, and marked it sure. It is a utility bill. The name rules stay on, and when they disagree with the model, the app asks.

Cost: an extra question now and then.

No model where it would demo best

A model deciding allow, hold or stop in Outpost would look impressive. It would also break the promise that the same action always gets the same answer, which is what makes the logbook auditable.

Cost: less flexible rules, by design.

What I measure

The numbers I watch in every AI feature.

Accuracy against a baselineDoes the model beat rules alone on a fixed test set?
Unsafe rateHow often it produces something harmful, kept at zero.
Flag rateHow often it says "not sure" instead of guessing, and whether that was right.
Median speedAgainst the wait the user will actually tolerate.
Fallback rateHow often the product runs without the model.
Override rateWith real users: how often people reject what it suggests.

The last one needs real users. In a pilot I would add time saved per task and cost per successful task.
